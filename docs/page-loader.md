# Индикатор загрузки страницы

Документ описывает, почему у SPA-навигации свой индикатор загрузки, чем ограничен родной индикатор браузера и при каких условиях имеет смысл перейти на Navigation API.

## Свой индикатор

Реализация — класс `NavigationLoader` в [npm/brandup-ui-website/source/loader.ts](../npm/brandup-ui-website/source/loader.ts). Это тонкая линия у верхней границы окна (CSS-класс `bp-page-loader`), которая ползёт вправо, пока идёт навигация или отправка формы.

### Жизненный цикл одной операции

1. `begin()` сбрасывает полосу в `0%` и возвращает номер операции;
2. через `SHOW_DELAY` полоса появляется сразу шириной `START_WIDTH` и едет до `SHOW_WIDTH`, а если операция затянулась дольше `STUCK_DELAY` — до `100%`;
3. `end(token)` доводит полосу до `100%` и прячет, но не раньше, чем от начала пройдёт `MIN_VISIBLE_TIME`.

`end` намеренно не снимает таймер появления: операция может уложиться в `SHOW_DELAY` (локальный сервер отвечает за единицы миллисекунд), и тогда переход прошёл бы вообще без индикатора. Полоса появляется всегда и живёт не меньше `MIN_VISIBLE_TIME`.

Появление начинается не с нуля: в базовом CSS-правиле у `width` нет `transition`, поэтому `START_WIDTH` применяется мгновенно и полоса сразу заметна. С нуля она первые доли секунды росла бы по `ease-in-out` на несколько процентов ширины — визуально это читается как «индикатор не показался».

### Номер операции

Навигации перекрываются: старт новой отменяет текущую (`__beginNav` в `@brandup/ui-app` вызывает `abort` у предыдущей), и отменённая раскручивается уже после того, как новая показала свою полосу. Поэтому `end` принимает номер операции, полученный от `begin`, и молча выходит, если полоса уже принадлежит следующей. Без этого завершение вытесненной навигации гасило полосу и чистило таймеры той, что её вытеснила — при быстрых кликах по ссылкам индикатор пропадал до конца загрузки.

### Связь с CSS

Значение `FINISH_DELAY` в `loader.ts` обязано совпадать с длительностью `transition` у класса `finish` (см. [npm/example-web-site/src/styles.less](../npm/example-web-site/src/styles.less)): через `FINISH_DELAY` после старта завершающей анимации класс снимается, и незаконченное затухание оборвётся скачком.

Класс `show` возвращается через `SHOW_DELAY` — это меньше кадра, поэтому сброс полосы в `0%` фиксируется отдельным пересчётом стилей (`void elem.offsetWidth`). Без этого браузер склеивает сброс и появление в один пересчёт, считает переход от прежней ширины, и полоса едет назад — от `100%` предыдущей операции к `SHOW_WIDTH` текущей.

### Полная перезагрузка

`keep()` оставляет полосу на экране: страница уходит в `location.assign` / `location.replace` / `location.reload`, документ ещё грузится, и прятать индикатор нельзя. Парный `end` после этого ничего не делает. Вызывается из `__forceNav` и из веток полной перезагрузки `__processPageResponse` в [middleware.ts](../npm/brandup-ui-website/source/middleware.ts).

## Родной индикатор браузера

Спиннер во вкладке в десктопном Chrome, полоса в адресной строке на Android, линия сверху в Safari — управлять ими из JavaScript нельзя. API нет ни для показа, ни для скрытия: индикатор жёстко привязан к жизненному циклу загрузки документа. Единственное доступное действие — прервать загрузку через `window.stop()`.

SPA-навигация через `history.pushState` документ не перезагружает, поэтому родной индикатор не включается — отсюда и необходимость своего. Он появляется только там, где мы уходим на полную перезагрузку, и как раз для этого случая существует `keep()`, чтобы две полосы не показывались одновременно.

Приёмы вроде скрытого `iframe` с медленным ресурсом, заставляющего браузер показать состояние загрузки, ненадёжны и вредят производительности — не используем.

## Navigation API

Единственный санкционированный способ заставить браузер считать SPA-переход настоящей навигацией:

```js
navigation.addEventListener("navigate", (e) => {
    if (!e.canIntercept || e.hashChange || e.downloadRequest !== null)
        return;

    e.intercept({
        handler: async () => {
            await app.nav({ url: e.destination.url });
        },
        scroll: "after-transition",
        focusReset: "after-transition"
    });
});
```

Пока промис из `handler` не разрешился, браузер:

- показывает свой индикатор загрузки;
- превращает кнопку «обновить» в «стоп», и она реально отменяет переход (`e.signal`);
- сам восстанавливает позицию прокрутки и фокус при возврате назад — то, что вручную собрано в [scroll.ts](../npm/brandup-ui-website/source/scroll.ts);
- корректно объявляет смену страницы скринридерам, чего `pushState` не делает.

Состояние записи истории при этом пишется через `navigation.updateCurrentEntry({ state })`, без `history.replaceState`.

### Почему не внедряем сейчас

- **Перехват должен жить в `@brandup/ui-app`, а не в этом пакете.** Сейчас клики по ссылкам ловит hyperlink-middleware и вызывает `app.nav()`. С Navigation API поток обратный: браузер сообщает о переходе, а `app.nav()` становится обработчиком. Это переработка ядра навигации, а не правка website-middleware.
- **Поддержка неполная.** В Chromium API есть давно, Safari подтянулся заметно позже, Firefox — последним; актуальные цифры сверять на caniuse. Свой индикатор всё равно остаётся как фолбэк, то есть появляется два пути навигации вместо одного.
- **Меняется семантика отмены.** Сейчас вытеснение навигации — собственный механизм (`__beginNav` → `abort`). С `intercept` отмену инициирует браузер через `e.signal`, и логику перекрытия придётся согласовывать с ним.

Ради одного индикатора переход не окупается: свой даёт полный контроль над видом и таймингами, а родной всё равно не покажешь во всех браузерах. Navigation API стоит рассматривать как отдельную задачу для `@brandup/ui-app` — там окупаются доступность, кнопка «стоп» и штатное восстановление прокрутки.
